# Human console contract

Read this only when changing the console generator, refresh handler, native helper or installation. Report content uses the delivery skill’s [console report contract](../../hwpx-workspace-delivery/references/console-report.md); it does not require this engineering contract. The opt-in record mode is described in [common records](../../hwpx-workspace-delivery/references/console-record.md).

## One work console

This is an optional, explicitly requested output. Ordinary work uses the supplied workflow and reports in chat without creating or refreshing `업무현황.html`, explanation TXT or another status/workflow file. Existing HTML is not implicit opt-in. When a console is requested, the single per-work `업무현황.html` displays analysis findings, pending questions, next actions, review and document links using the existing generator. School artifacts such as HWPX/XLSX are created or revised only when the requested result requires them. Existing human files are preserved unless their removal is separately authorized. The following display rules apply only to a requested console.

- For an explicit console request, generate one `업무현황.html` directly under the selected work folder. The first and default tab is `workflow`, left of `홈`. Preserve the existing workflow/Home tab IDs and checkbox storage keys. Render chronological steps directly, without an `업무 현황` disclosure. Render registered report sections expanded in Home before the document list; keep current files and the existing `확인 요청` there. Do not add an `업무정리` tab. Pending questions and next actions remain readable in the report; do not require another document to see them. Keep legacy nextAction text visible in workflow when structured steps are absent. Receipt time belongs in a small muted-gray footer aligned right, formatted `yyyy-MM-dd HH:mm`.
- New work plans follow [workflow-format.md](../../work-planning/references/workflow-format.md): period, short title, newline-separated actions, optional evidence-backed completion criterion, and collapsed evidence. Prior-period plans remain visibly tentative. Load source ledgers and memoize source hashes only within one console generation; a later refresh rechecks them.
- Checklist plans use stable step/item IDs, item text, registered per-step references, completion criteria and confirmation questions. Keep all steps visible; dim completed steps and highlight the first incomplete step. Scroll there on initial workflow opening or explicit resume, never while checking an item. Store only booleans in browser localStorage, keyed by file pathname; disclose browser/location scope and storage failure. Legacy action lines render as checks with content-derived IDs; legacy nextAction prose remains intact. Existing IDs must survive wording-only plan updates.
- On Windows, setup/installation sets the Hidden attribute on cabinet `.agent` and work `.ai` directories, preserving other attributes and rejecting reparse points. Intake applies it to new/reused metadata. Do not change Explorer preferences; users enabling hidden-item display may still see these folders. File operations must use explicit paths or `-Force` where internal enumeration is required.
- Show actual workflow/support folders as tabs and registered sources in one `업무근거` tab grouped by original parent location. Numbered folders come from the user's requested workflow, including added tasks; do not create unrelated empty categories. A singleton step may be a numbered root file, and major/frequent-reference files remain at the root. Storage paths and step IDs are separate; retain checklist IDs on additions and wording changes. User-specified order is labeled as such, not as official current evidence.
- Reflect visible files added/renamed/removed by the human, including the root, without changing current-file registration or source authority. Registration mismatches still block document follow-up/publication, not a read-only listing refresh or requested communication-only report; include their counts in the console receipt.
- Existing local TXT content may be displayed, but report delivery never generates an explanation TXT. New TXT artifact publication requires an explicit user request and the `-ExplicitTextArtifact` gate; a generic request for a summary or final result is insufficient. Exclude credentials, secrets, `.ai`, hidden/system items, and reparse-point descendants from file listings and open targets. The generator may read approved user-facing metadata fields such as `consoleContent` from `.ai/work.json`; this does not expose the metadata file itself.
- File-open links launch from HTML directly through the registered `hwpx-work-open:` native helper. Only manifest-listed, non-executable paths are allowed; revalidate on dispatch. Shortcuts are not document manifest targets. Successful dispatch is silent apart from the requested document opening in its associated app: no intermediate chooser, launcher window, visible shell or extra confirmation UI. This does not suppress or bypass browser/OS permission prompts.
- The native helper opens files and delegates refresh to the existing handler in a hosted Windows PowerShell 5.1 session, waiting for its result. The handler handles refresh only. Its process-scoped execution policy matches the workspace script invocation; never change persisted execution policies or browser profiles/policies. The user handles any one-time browser permission prompt. The native response records `status`, `dispatched`, `opened: null`, `stage`, `exitCode` and request correlation. Request-specific markers prevent concurrent clicks from overwriting responses. Unknown or pre-registration failures remain internal diagnostics; no untrusted destination is written. HTML acknowledgement timeouts must not infer that a permission prompt exists or that the browser blocked execution; report only the missing acknowledgement.
- F5 or the title banner initiates refresh through the native anchor action after a user gesture. Reload only after a matching, bounded acknowledgement, using a request-specific query to avoid an old cached page and retaining the selected tab.
- `Start-HwpxWork.ps1`, `Publish-HumanResult.ps1` and `Prepare-WorkWorkflow.ps1` leave HTML unchanged by default. Use `-UpdateConsole` only when the user requested console creation/update with that operation. Direct `Update-HumanWorkConsole.ps1` and `ConsoleContentPath` remain explicit console routes. A requested Setup refreshes existing consoles only; it must not create missing ones.
- The cabinet runtime is the single protocol-registration authority. Calling `Register-HumanWorkOpenProtocol.ps1` from the maintenance workspace delegates to the installed cabinet; `-BuildOnly` never registers. Location repair, Setup and workspace checks use that same executable and manifest. If a cached association still invokes the maintenance executable, it resolves its configured cabinet before validation and dispatch; explicit test manifests remain isolated. Do not register the workspace executable to repair a successful cabinet registration.
- Console use requires an installed cabinet runtime. Intake never installs it automatically. For a requested update to an existing installation, use `Install-PortableCabinet.ps1 -RuntimeOnly`: it replaces only the shared scripts and executable, preserving settings, registration, documents and HTML. Full installation and `Setup.cmd` are separate maintenance operations. Runtime diagnostics go to the system temporary directory and do not depend on historical diagnostic folders.
- `Test-CabinetLifecycle.ps1` exercises delivery orchestration with synthetic artifacts; it does not verify Hanword editing/rendering gates. Any synthetic TXT publication must explicitly model a requested text artifact rather than bypass the gate.
- A cabinet relocation is explicit: use `Set-HumanCabinetRoot.ps1 -CabinetRoot <selected path>` to inspect and `-Apply` to select it. `-ExpectedPreviousRoot <old path> -BindLegacyJobs` adds stable IDs only to verified legacy bindings. This does not move documents, rewrite provenance, register a protocol or regenerate HTML. Archived cabinets can be selected as prior reference materials without changing the active cabinet. For explicitly requested portable-console relocation, use the selected cabinet's `Initialize-PortableCabinet.ps1` separately; existing console paths and browser-local checkbox state require their own verification. Never infer a replacement cabinet from a sibling folder name.

## Maintenance verification

Select affected checks from [the maintenance check map](checks.md), deduplicating commands across changed components. Documentation-only changes stop at format, links and representative request decisions. Do not regenerate production consoles for tests. Code/native results and actual browser-click results are different evidence; do not claim the latter from dispatch alone. If file-URL access is blocked, report that unperformed check without bypassing the policy.

No cabinet-root dashboard or index generator. Preserve existing per-work consoles and update them only when requested. Prior materials use only user-selected paths; do not create year folders or recreate removed diagnostic state.
